§26.1部署链路与压缩

  1. 导出：PyTorch → ONNX（注意动态轴、算子兼容、自定义算子）；或直接用 TorchScript / 引擎原生格式。
  2. 选引擎：服务端 GPU 用 TensorRT，跨平台 CPU/GPU 用 ONNX Runtime，Intel 边缘用 OpenVINO，移动端用 ncnn / TFLite。
  3. 压缩：PTQ（训练后量化，需校准集）快但可能掉点；QAT（量化感知训练）更稳但需重训；结构化剪枝减通道，蒸馏把大模型能力迁到小模型。
  4. 验证：逐层比对浮点与量化输出、测 P50/P99 时延与内存峰值、在目标硬件上而非开发机上验收。
pip install onnx onnxruntime onnxsim
python -c "import onnx, onnxruntime; print(onnx.__version__, onnxruntime.__version__)"

§26.2数据闭环

上线不是终点。一个可维护的视觉系统需要：标注规范与抽检（CVAT / Label Studio）→ 数据集版本化 → 训练/评测脚本版本化 → 难例回流 → 定期回归测试集 → 线上分布漂移监控。回归测试集应包含历史出错样本与关键切片，每次发版都跑，防止“改 A 坏 B”。

最常见的事故不是模型不准，而是预处理不一致：训练用 RGB + 归一化为 [0,1]，部署用 BGR + 0～255；或训练与推理的 resize / padding 策略不同。务必把预处理写进同一份配置并与模型一起导出。

§26.3综合课程设计：两条基线同台

题目（与第 15 章完全相同的颗粒计数任务）要求交付两份实现：

维度传统基线深度基线
实现第 15 章 Octave 流水线U-Net / YOLO 实例分割（任选其一）
数据需求一张图 + 少量调参标注集、划分文件、训练脚本
可解释性每步可写公式、参数有物理含义需消融与热力图
失效方式光照/粘连/噪声破坏假设分布外、标注偏差
工程成本零依赖、CPU 秒级GPU、权重管理、部署链路

报告必须回答：哪些环节值得换成网络？换成网络后，可解释性、数据成本与维护成本各增加了多少？给出定量对比表（计数误差、面积误差、推理时延、标注工时、代码行数），而不是只给一句“深度学习更准”。

§26.4伦理、偏差与交付清单

  • 标注与训练数据的人群/场景覆盖是否均衡，关键切片指标是否单独报告；
  • 出错时的降级策略（低置信度转人工、规则兜底）；
  • 模型权重、数据集、预处理配置、随机种子与评测脚本是否齐全；
  • 外部依赖的许可证与数据来源是否合规；
  • 是否存在会误导下游的“看起来更好”的指标（第 19、23 章）。

§常见误区

  • 只在开发机上测时延：目标硬件的内存与算子支持可能完全不同。
  • 训练与推理预处理不一致：最常见、最隐蔽的线上精度事故。
  • 没有回归测试集：每次优化都可能悄悄破坏旧场景。
  • 只比精度不比标注工时与维护成本：结论对工程决策没有价值。
